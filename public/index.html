CWE-89 · OWASP A03:2021 · MITRE T1190

Injection SQL basée sur le DOM

Analyse formelle, démonstration reproductible et évaluation des contre-mesures sur une base MySQL réelle.

§ 1

Abstract

L'injection SQL basée sur le DOM est une variante de CWE-89 où la charge malveillante n'est pas saisie dans un formulaire, mais lue directement depuis un nœud du Document Object Model — typiquement location.hash ou location.search. L'attaquant n'a besoin que d'envoyer un lien à la victime : l'ouverture suffit à déclencher l'injection, sans aucune interaction avec l'interface.

Cette étude présente une analyse systématique du vecteur, une taxonomie des techniques d'exploitation, une plateforme reproductible sous MySQL 8 / XAMPP / Node.js, et une évaluation empirique de six techniques d'attaque et de trois contre-mesures. Chaque affirmation est accompagnée d'une preuve d'exécution : requête SQL réelle, lignes exfiltrées, latence mesurée.

1

Source non fiable

Le vecteur provient du navigateur, pas d'une entrée HTTP classique.

2

Déclenchement passif

Un simple lien partagé suffit — pas de formulaire à remplir.

3

Preuve live

Extraction de mots de passe bcrypt et de clés d'API en clair.

Contributions

  1. Modèle formel du flux de données non fiable (source → sink SQL).
  2. Taxonomie étendue : UNION, boolean, time, error, out-of-band, stacked.
  3. Plateforme reproductible : XAMPP + MySQL 8 + Node.js, seed versionnée.
  4. Comparaison côte à côte des requêtes SQL vulnérable vs sécurisée.
  5. Métriques forensiques : latence, volume, journalisation structurée.
§ 2

Modèle de menace

Un modèle de menace formalise ce que l'on protège, contre qui, et sous quelles hypothèses. Sans lui, une démonstration d'attaque n'est qu'une anecdote.

Hypothèses adverses

A1
Canal de persuasion

L'attaquant peut envoyer un lien à la victime (email, chat, QR code).

A2
Visite passive

La victime ouvre le lien mais n'interagit avec aucun formulaire.

A3
Pré-authentification

Aucun compte valide n'est nécessaire pour déclencher l'attaque.

A4
Confiance aveugle du backend

Le serveur suppose que category est une valeur contrôlée.

A5
Absence de défense

Pas de WAF, pas de validation d'entrée, pas de requête préparée.

Flux formel

Soit Σ = (S, T, K) le système observé :

  S = { location.hash, location.search, document.referrer, postMessage }
  T : S → ℝ              (transport : fetch, XHR, form-action)
  K : ℝ → SQL            (construction : concaténation, template, ORM)

Une injection est possible  ⟺
    ∃ s ∈ S,  ∃ t ∈ T,  ∃ k ∈ K  tels que
    k(t(s)) contient un opérateur SQL interprétable.

Une contre-mesure est correcte  ⟺
    k est paramétrée : la donnée est séparée du code avant analyse.

§ 3

Taxonomie des techniques

Toutes les injections SQL ne se ressemblent pas. Choisir la bonne technique dépend de ce que le serveur renvoie et de ce qu'on peut mesurer.

①

Quote probing

Idée : envoyer un ' et voir si MySQL renvoie une erreur.

Signal : erreur de syntaxe SQL (code 1064).

Usage : première étape — confirme que l'entrée n'est pas échappée.

②

Boolean-based

Idée : poser une question vrai/faux (1=1 vs 1=2) et observer le nombre de lignes.

Signal : différence de volume de résultats.

Usage : extraire de l'information bit par bit.

③

UNION-based

Idée : ajouter une seconde requête avec UNION SELECT pour lire une autre table.

Signal : colonnes étrangères dans la réponse.

Usage : extraction massive — la plus rentable.

④

Error-based

Idée : forcer MySQL à mettre une donnée dans un message d'erreur (extractvalue).

Signal : la donnée apparaît dans le texte de l'erreur.

Usage : quand le serveur renvoie les erreurs brutes.

⑤

Time-based blind

Idée : injecter SLEEP(3) et mesurer la latence.

Signal : réponse anormalement lente.

Usage : quand rien n'est renvoyé — la plus discrète.

⑥

Out-of-band

Idée : forcer MySQL à faire une requête DNS/HTTP vers un serveur contrôlé.

Signal : callback reçu sur le serveur attaquant.

Usage : quand la réponse HTTP est totalement muette.

Résultats expérimentaux

Chaque payload a été exécuté 30 fois contre la stack XAMPP / MySQL 8.0.36. Les latences sont des médianes, en millisecondes.

Observations

①

UNION offre le meilleur rapport effort/information : un seul appel suffit à dumper une table entière.

②

Time-based est le plus lent mais le plus discret : aucun signal dans la réponse HTTP, seule la latence trahit l'attaque.

③

Quote probing est bruyant (erreur SQL en clair) mais indispensable en phase de reconnaissance.

④

Les mots de passe en clair dans la base rendent l'impact maximal : aucune protection résiduelle.

§ 6

Contre-mesures

Une seule contre-mesure est structurellement correcte : la requête préparée. Toutes les autres sont des défenses en profondeur, utiles mais non suffisantes.

C1 · Obligatoire

Requête préparée / paramétrée

Principe : la requête est analysée par MySQL avant que la donnée y soit insérée. La donnée ne peut donc jamais devenir du code.

❌ Vulnérable "... WHERE category = '" + input + "'"
✅ Sécurisé "... WHERE category = ?"

→ Neutralise 100% des injections SQL connues.

C2 · Défense en profondeur

Validation par liste blanche

Principe : rejeter toute entrée qui ne correspond pas à un motif strict (lettres, chiffres, espace, tiret).

→ Efficace mais peut rejeter des entrées légitimes. Ne remplace jamais C1.

C3 · Réduction d'impact

Hachage bcrypt des mots de passe

Principe : même si l'attaquant exfiltre la table users, il obtient des hashs — pas des mots de passe en clair.

→ Ralentit le cracking offline (250 ms/tentative à coût 12) mais n'empêche pas la fuite.

C4 · Hygiène

Suppression des erreurs SQL brutes

Principe : ne jamais renvoyer SQLSTATE[42000]: Syntax error... au client. Bloquer la technique error-based et le fingerprinting.

→ Empêche l'attaquant d'apprendre la structure de la base.

C5 · Détection

Journalisation structurée

Principe : logger chaque requête SQL avec IP, timestamp, latence. Détecter a posteriori les motifs UNION, SLEEP, 1=1.

→ Indispensable en production. Ne bloque pas mais permet la réponse à incident.

Ce qu'il ne faut PAS faire

✕
Échapper manuellement les guillemets

Contournable par encodage, commentaires, casse. Faux sentiment de sécurité.

✕
Blacklister des mots-clés

Contournable par UN/**/ION, casse alternée, encodage URL.

✕
Se reposer sur un WAF seul

Un WAF détecte des signatures, pas des sémantiques. Contournable par obfuscation.
